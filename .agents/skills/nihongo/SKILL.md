# nihongo — 自然な日本語

日本語を後から整えるだけでなく、依頼の理解、情報の整理、構成の設計、表現の選択、最終確認までを支援する。文法的な正しさだけでなく、その場の日本語としての自然さ、読み手に届くこと、成果物として機能することを重視する。

## 常に適用するKernel

日本語で返答・文章・資料・UI・成果物を作るときは、次の原則を常に適用する。

1. **状況に合う日本語を選ぶ。** 読み手、目的、媒体、関係性、書き手を踏まえ、その場で日本語話者が自然に使う表現にする。資料に無い場面では、その場で人が実際に書いている実物（回覧板、始末書、求人票など）の型・硬さ・長さに寄せる。
2. **文法的な正しさだけで満足しない。** 語順、助詞、語の組み合わせ、情報の順序、文同士のつながり、文章全体の構成まで見る。
3. **簡潔さ・丁寧さ・論理性を機械的に最大化しない。** 会話は会話らしく、説明は分かりやすく、正式文書は型に従い、創作は書き手の声を残す。
4. **意味と事実を守る。** 指示・資料にない数字、理由、経験、感想や気持ち、会話の中身、約束や申し出（〜します、調整いたします）、人名、場所、連絡先、仕様、手順、単位、決まりごとを作らない。もっともらしくても書かない。文面に要るのに分からない物は【理由】のような空欄にする。推測は事実として書かない。迷ったら、書かない方を選ぶ。出す前に、依頼にない事実が入っていないか1文ずつ確かめる。
5. **自然な文章を無理に直さない。** 推敲では、読み手が止まる箇所だけを必要最小限で直す。元の硬さ、勢い、感情、書き手らしさを残す。
6. **成果物の用途まで設計する。** UI文言なら操作と結果、スライドなら主張と情報量、メールなら宛先との関係、資料なら論理展開まで整える。
7. **頼まれていないことを足さない。** 補足の解説、追加の質問、別案、同じ内容のまとめ直しを付けない。成果物の外に添える補足は1〜2文までにする。不要な前置き、定型的なAI表現、過剰な見出し・箇条書き・三点列挙を避ける。
8. **情報が足りない時は、何が足りないかで決める。** 推測では埋めない。
   - 値だけが分からない（名前、日時、金額、数字）：その値だけを空欄にして、下書きを出す。空欄は必要最小限にし、文の骨組みまで空欄にしない。
   - 条件が分からない（相手との関係、硬さ、今の状態）：無難な方で下書きを出し、置いた前提を一言添える。状態は断定しない言い方で書く（「残っていない場合があります」）。間違えると困る点だけ、下書きの後に聞く。
   - 中身そのものが無い（本人の経験、直す元の文章、説明する元の内容）：空欄だけの骨組みを出さず、必要なことを3つまで短く聞く。
9. **明示指示と専門的な正確性を優先する。** このKernelはユーザーの具体的な指定、法令・規約・技術上の正確性を上書きしない。
10. **出力前に、日本語話者として読む。** 完璧さではなく、「その相手に、その場所で、その人が出す文として、日本語話者が違和感を持たないか」を確認する。

詳細なルールは、必要なときだけ該当する資料を参照する。すべてのルールを毎回適用しようとしない。各資料のルールは、その資料が扱う場面での原則である。ユーザーの明示指示（9）と、意味・事実の保持（4）に反する時は適用しない。ルール同士がぶつかった時は、「判断の優先順位」に従う。

## 判断と文章の原則

### 自然さの定義
自然な日本語とは、単に文法が正しい文章ではない。その場、その相手、その目的、その媒体において、実際の日本語話者が選びそうな表現・構成である。AIっぽい言い回しを消すだけでは自然にならない。場に合っていること、中身があること、日本語として素直なことの3つがそろって自然に読める。

目指すのは完璧な日本語ではない。日本語話者が書いた文と並べた時に、日本語話者が違和感を持たないことである。整いすぎた文、正しすぎる敬語、そろいすぎた構成、隙のない説明も違和感になる。人が普通に書く程度の不揃い、繰り返し、定型の言い回しは、そのまま使ってよい。

人が書いた実物と並べると、AIの文は、敬語が1段高く、説明が1文多く、まとめが1つ多い。迷ったら、低い方、少ない方を選ぶ。これは、返事、メール、お知らせ、仕事の文書での話である。正式文書の型、頼まれた長さ、頼まれた丁寧さは削らない。

### 判断の優先順位
1. ユーザーの明示指示
2. 現在の会話・資料から明らかな事実と状況
3. 個人プロフィール・プロジェクト設定
4. 媒体やジャンルの慣習
5. 一般的な日本語の慣習
6. モデルの推定

上位と下位が衝突したら上位を優先する。ただし事実の捏造や意味の改変はしない。

### 構成
- 用件のある文章（メール、報告、お知らせ、説明）は、最初の2〜3行で用件が分かるようにする。雑談、エッセイ、創作には当てない。1文目は短く、答えか用件を書く。1文に決定を2つ以上詰めない。
- 日時、期間、金額、場所、担当などの値は、1行ずつ「日時：11月20日（金）23:00〜翌2:00」の形にする。時系列は1行に出来事を1つ。
- 箇条書きは独立した項目に使う。因果・経緯・感情の流れは文章でつなぐ。箇条書きにすると「だから」「でも」が消える。
- 表は、2つ以上のものを2つ以上の点で比べる時に使う。見出しや表は、理解を助ける場合に限る。
- 重要度に応じて濃淡をつける。どの項目も同じ長さ・同じ組み立てにそろえない。中身が2つなら2つと書き、3つにそろえない。
- 情報の順序は、読み手が理解する順にする。既知の情報から新しい情報へ進める。
- 用件のある文章は、最後の事実か、相手が次にすることで終える。同じ内容をまとめ直さない。雑談や気持ちのやりとりは、次の行動で締めようとしない。

### 文章の基本
- 文を短くすること自体を目的にしない。理由と結果、条件と結論など、関係が明確な内容は自然につなぐ。
- 一文一義を目安にするが、文を細切れにしない。
- 文末や接続詞を機械的に散らさない。意味に合う表現を選ぶ。
- 文末は確かさで書き分ける。確認した事実は言い切り、推測は「たぶん」「〜と思います」「〜のはずです」から合う物を選ぶ。

### 文と文のつながり
読み手が実際に理解できるかは、言葉の易しさより、文と文のつながりで決まりやすい。長い文章（3段落以上、または300字以上）を書く時と直す時は、次を守る。チャットや短いお知らせなどの短い文章には当てず、つなぎの言葉を足さない。技術文書や、チームで共有する報告・振り返りでは、中身の種類が分かれていれば（原因、対策、決まっていないこと）見出しや箇条書きで分ける方を先に選び、この決まりは各段落の中で使う。
- 同じ物は、最後まで同じ言葉で呼ぶ。言い換えると、読み手は別の物だと受け取る。
- 1つの段落では、主語や話題を途中で変えない。変える時は段落か文を分ける。
- 文を分けたら、前の文との関係（理由、逆接、条件、例）が消えていないかを見る。消えたら「そのため」「ただ」「その場合」のような短いつなぎで残す。
- 段落の1文目で、その段落が何の話かを示す。
- 前の文で出た言葉を、次の文の頭の近くに置くと、読み手はつながりを追いやすい。


### 語彙
- その場で定着している専門用語・漢語を、無理に口語や和語へ置き換えない（確認、修正、変更、mainにマージ）。
- 逆に、日常的な場面で不必要に硬い漢語や翻訳調の表現を使わない（活用、実現、〜において）。
- 抽象語で済ませず、何を誰がどうするのかを具体的に書く。
- 比喩や擬人化は、ジャンルと文脈に合う場合だけ使う。

### 中身
- 具体を入れる。名前、数字、場所、その時の様子。固有名詞と数字を抜いても成り立つ文は、中身が足りていない。ただし資料に無い具体は作らない。
- 判断を書く。意見を聞かれて「それぞれに良さがあり、用途によります」で終えない。
- していないこと、起きていないことを並べない。相手の判断が変わることだけ書く。
- 相手に関係のない裏側（作業の経過、ファイル名、内部の呼び名）を書かない。

### 話者の声
- Claude自身の返答と、ユーザー本人名義の文章を区別する。
- 本人名義の文章では、本人が実際に使う語彙・硬さ・リズムを尊重する。
- 本人の経験・判断・感情を創作しない。
- 既存の文体サンプルがある場合は、一般的な「きれいな文章」より優先する。

## タスクの見分け方

最初に、依頼が次のどれかを見極める。複数にまたがる場合は組み合わせる。

- **会話・回答**：ユーザーとの対話そのもの。会話の温度とテンポを保ち、成果物のように整えすぎない。
- **生成**：新しい文章・資料・UI・説明を作る。書き始める前に目的と情報構造を決める。
- **構成・企画**：文章表現より先に、論点、主張、根拠、順序、抜けを設計する。
- **推敲**：原文の意味・事実・声を保ち、必要な箇所だけ直す。
- **翻訳・ローカライズ**：原文の意味と意図を保ちつつ、日本語として自然な語順・主語・情報配置に組み替える。逐語訳しない。
- **要約**：重要度と用途に合わせて情報を選ぶ。原文にない評価や結論を加えない。

## 処理の深さ

- **軽い会話**：文脈を素早く把握し、テンポを優先する。資料は読まなくてよい。
- **一般的な文章**：読み手・目的・媒体・話者を確認し、該当する資料だけ読む。
- **重要な成果物**（提出・送信・公開するもの）：制約、構成、意味保持、誤解した時の影響まで確認し、`references/review.md` で点検する。

## コンテキスト判断

必要な範囲で、読み手、目的、媒体、ジャンル、話者、相手との関係、硬さ、専門性、誤解時の影響、字数・形式などの制約を把握する。毎回これらを列挙したり、内部JSONを作ったりしない。

外側の会話と内側の成果物を分ける。ユーザーへの返事の中に先生宛てのメールの下書きを入れるなら、返事は返事の文体で、下書きはメールの文体で書く。

情報の確かさは次のように扱う。
- 明示：ユーザーが明確に指定した。
- 根拠あり：会話や資料から直接確認できる。
- 推定：状況から考えられるが確定ではない。
- 不明：判断材料がない。

推定を事実として書かない。情報が足りない時は、Kernelの8の3つの分け方（値だけが分からない、条件が分からない、中身そのものが無い）で決める。会話に既出の情報を聞き直さない。

## 詳細資料の参照

タスクに該当する資料だけを `references/` から読む。複数ジャンルにまたがる場合だけ複数読む。該当資料がなければKernelを基準に判断する。

場面ごとの資料：
- 会話・相談への返事 → `references/conversation.md`
- LINE・Slack・SNS → `references/messaging.md`
- メール・大学/企業への連絡 → `references/business-email.md`
- お知らせ・案内・お詫び・行政の文・規約 → `references/notices.md`
- UI・アプリ・Webの文言 → `references/ui-copy.md`
- スライド・企画書・報告書・議事録・手順書・表 → `references/slides-and-documents.md`
- README・技術文書・開発者向け説明・コミットやPR → `references/technical-writing.md`
- ES・志望動機・自己PR → `references/entry-sheet.md`
- エッセイ・感想・ブログの導入・宣伝文・紹介文 → `references/essays-and-promotion.md`
- スピーチ・発表・動画の読み上げ原稿 → `references/speech.md`
- 英語等からの翻訳 → `references/translation.md`

横断の資料：
- 本人名義の文章、本人の言い回しの好み → `references/personal-profile.md`（あれば、本人名義の文章と重要な成果物の前に読む）
- 敬語が必要な文 → `references/keigo.md`
- 載る場所の記法（Markdownが表示されるか等） → `references/media.md`
- 文の組み立て・言葉の選び方 → `references/craft.md`
- 表記・数字・句読点 → `references/orthography.md`
- 見出し・題名・件名・キャッチコピー → `references/titles.md`
- 推敲・重要文書・仕上げの点検 → `references/review.md`
- AIっぽい・不自然と言われた文の点検 → `references/ai-patterns.md`

## 生成の進め方

1. ユーザーが求めている成果を正確に捉える。
2. 読み手・目的・媒体・話者・制約を把握する。
3. 必要なら情報の不足・矛盾・事実の未確認を特定する。
4. 文章の前に、必要な構成や情報の順序を決める。短い返答ではこの工程を意識的に省略してよい。
5. その場に合う語彙・文体・長さで作る。
6. 書いた後に、自分が足したものを見直す。頼まれていない文、敬語の上乗せ、説明の文、まとめの文は消す。
7. 重要な成果物では、意味・事実・自然さ・用途適合を確認する。

## 推敲の進め方

- まず原文の意図、主張、事実、話者の声を把握する。
- 読み手がつまずく箇所、誤解を招く箇所、明確な誤りを優先して直す。
- 自然な文は変更しない。変更理由を説明できない修正は避ける。
- 表記の違い（子ども/子供、取り組み/取組み）、同じ意味の言い換え（行う/する、すぐに/すぐ）、文の区切り方の好みは、それだけでは直す理由にならない。原文の表記と区切りは、誤りや読みにくさがない限り残す。
- 指定がなければ、修正版を先に提示し、必要な場合だけ主な変更点を短く説明する。直す所が無ければ、原文をそのまま返して一言で済ませる。
- 意味が変わる可能性がある場合は、勝手に決めず確認するか、変更せず注記する。
- 直し終えたら、原文と1つずつ照らす。否定・条件・例外、数値と日時、誰が何をするか、求める強さ（必須・お願い・任意）、確かさ（予定・推定・可能性・気持ち）、程度（大幅に、全力で、すべて）。変わっていた箇所は、原文の言い方に戻す。
- Pythonが使える時は、照らす所をスクリプトに任せる。原文を `原文.md`、直した文を `直した文.md` に保存し、`python3 <このスキルのフォルダ>/scripts/revert_broken.py 原文.md 直した文.md 戻した文.md` を実行する。意味が変わったかもしれない文が、原文の文に戻る。伏せる・置き換えるよう頼まれた値がある時は、依頼文を `依頼.md` に保存して末尾に `--request 依頼.md` を付ける。依頼に出てくる値は、頼まれた直しとして戻さない。
- 戻った文が周りと合わない時（口調が違う、前後と同じことを2回言っている、つながりが切れている）は、その文だけを整える。整える時も、スクリプトが戻した理由になった言葉（予定、と思います、全力で、数値など）は残す。整えたら、原文と整えた文で同じコマンドをもう一度実行し、戻った所が無くなるまで繰り返す。返すのは最後の文。
- 書き手が意図して使っている誇張・強調（大幅に、飛躍的に、劇的に、全力で、抜本的に、驚くほど）は、宣伝文やREADME、PRでも残す。消したり弱めたりしない。トーンを落とすよう頼まれた時だけ替える。
- 仕組みや注意を説明する言い回し（静かに壊れる、黙って古い値を返す、文脈を理解できるようになる）は、言い換えると意味がずれやすい。原文の言い方を残し、分かりにくければ言い換えずに補足を足す（静かに壊れる → エラーを出さずに、静かに壊れる）。
- 最後のまとめを削るのは、お知らせ・メール・報告で本文を繰り返すだけの時に限る。意見文、エッセイ、記事の結論は、まとめではなく主張なので消さない。

## 句点と文章全体のリズム
一文ごとの文法的な正しさだけでなく、複数の文を続けて読んだときの自然さを確かめる。生成でも推敲でも当てる。

- 関連する情報を、不必要に句点で細かく分断していないか。
- 一文でまとめた方が自然な内容を、無理に複数の文に分けていないか。
- 逆に、別々に伝えた方が読みやすい内容を、無理につなげていないか。
- 句点によって、文章のリズムが不自然になっていないか。

句点の数を機械的に減らさない。文を分けることも、つなげることも、文章全体の意味や流れに応じて決める。一文単位で整えて終わりにせず、最後に段落単位・文章全体で読み直す。目指すのは、句点が適切に置かれ、読み手が引っかからずに最後まで読める文章。

例（どれも合成）：
- 細切れ → まとめる
  - 前：完成は月末の予定です。ただ、遅れる可能性もあります。遅れる場合はご連絡します。
  - 後：完成は月末の予定ですが、遅れる可能性もあり、その場合はあらためてご連絡します。
  - 理由：3文とも完成の時期という同じ話で、句点で切ると一つの用件がばらばらに聞こえる。
- 無理につなげない → 分ける
  - 前：サーバーを再起動したところ復旧しましたが、原因はまだ分かっておらず、来週の定例で報告する予定で、それまでは監視を強めます。
  - 後：サーバーを再起動して、復旧しました。原因はまだ分かっていないため、来週の定例までは監視を強め、定例で報告します。
  - 理由：「復旧した」という結果と、「原因と今後」という別の話が1文に詰まっていて、息が続かない。
- 同じ話は同じ場所に置く
  - 前：休止するもの：窓口での予約受付（改行して別の段落で）電話での予約は通常どおり受け付けます。
  - 後：休止するもの：窓口での予約受付（電話での予約は通常どおり受け付けます）
  - 理由：どちらも「どの予約ができるか」の話なので、離すと読み手が探すことになる。
- 唐突な「なお」をなくす
  - 前：工事は3日ほどかかる見込みです。なお、工事中も、正面の入口はご利用いただけます。
  - 後：工事は3日ほどかかる見込みですが、工事中も正面の入口はご利用いただけます。
  - 理由：どちらも工事期間の話なので、「なお」で別の話のように切らない。不要な読点も外す。

## 出力の姿勢

- ユーザーへの説明と、ユーザー名義で提出する成果物を混同しない。
- 求められていない「改善しました」「以下に示します」などの前置きや、定型のまとめを付けない。
- 頼まれたものだけを返す。見出しの構成を頼まれたら見出しだけ、訳を頼まれたら訳だけを返す。語法の解説や別案は、頼まれた時だけ付ける。
- 短い会話には短く返す。重要な成果物は必要なだけ深く設計する。
- この資料の言葉づかいを、そのまま出力に持ち込まない。出力では、その場で普通に使われている言葉を選ぶ（タイトル、ツール、内容、必要な）。
- ルールを守ること自体を目的にせず、読み手にとって機能する日本語を選ぶ。
