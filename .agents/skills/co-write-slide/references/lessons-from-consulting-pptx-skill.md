# consulting-pptx-skill から取り入れる点

[carnot-tech/jinba-consulting-pptx-skill](https://github.com/carnot-tech/jinba-consulting-pptx-skill)(MIT、旧名 consulting-pptx-skill、2026-11-12 の版 1d62cd1)を読み、co-write-slide に効く点だけを抜き出した。原文は経営会議や提案書のための規約で、勉強会や登壇の発表とは前提が違う。そのまま規則にせず、フェーズ1で AI が自分の案を書くときの点検と、フェーズ2で発表者に問うときの材料に使う。

どれも発表者の判断より下に置く。発表者が示した流れや文言と食い違ったら、発表者に従う。

## 発表者の構成と言葉を守る

- 発表者がページの並びを渡したら、組み替えずにそのまま使う。順序を変えるのは、前提が後ろにある、同じことを2回言っている、のように論理が崩れているときだけで、その場合も理由を1行添えて確かめる。「並べ替えたほうがきれい」は理由にならない。
- 発表者が書いた文言と、指摘を受けて直した文言は確定したものとして扱う。版を作り直すときに前の言い回しへ戻したり、黙って言い換えたりしない。
- 前の版で発表者が消したページや言い回しは、手元の型やスクリプトにあっても作り直さない。
- 指示された箇所だけを直す。ついでに直したくなった所は、直さずに提案として添える。
- 発表者が手で直したページがあれば、それを正として他のページをそろえる。直す前に最新のファイルを読み直す。

## 各ページに目的があるか

- 表紙と扉を除く全ページについて、「このページで伝えたいこと」を1行ずつ書き出す。書けないページは削る候補で、フェーズ2の「要るか」の問いに回す。
- 調べた量と載せる量を分ける。聞き手の受け取り方を変えない情報(調べた過程、周辺の事実)は載せない。技術の勉強会に市場調査を混ぜない、のように、発表の種類から外れる材料も同じ。
- 発表者が強調した証拠は、別のページの箇条に埋めず、1枚を取る。

## タイトル

- タイトルだけを切り出して、初見の人が意味を取れるか。主語や対象を落とした圧縮語にしない。「この」「その」で別のページを指さない。
- ページの中身の個数(「3つの理由」「5段」)をタイトルに入れない。個数は主張ではない。数を書くのは、その数自体が伝えたいこと(「3 倍になった」「17/24」)のときだけ。
- 数を書いたら、ページの中身と一致させる。「3段階」と書いて矢印が4本、は聞き手が最初に気づく破綻。
- 課題や打ち手を3つにそろえない。数は材料で決める。

## 同じことを2回言わない

- 後半のページが前半の内容を言い直しているだけなら削る。文言が違っても、似た含みの繰り返しはくどく聞こえる(例: 「AI の推論は無し」と「LLM に頼らない」と「LLM に座標を推測させない」)。
- 図とその説明文、表とその直後の箇条が同じことを言っていないか。動画の一覧表と、その動画を流すスライドが並んでいないか。
- どうしても2か所で触れる内容(冒頭の予告と締めなど)は、同じ言葉で短く呼び戻す。言い換えると、聞き手は別の主張だと受け取る。

## AI らしさの3つの出どころ

1. どの構造にも属さない、浮いたラベルや小さな箱
2. 箇条にせず流し込んだ長い説明
3. 主語と述語を抜いた圧縮語(「精度向上」「連携強化」)

あわせて、丸括弧の多用、「ポイントは3つ」の型、信号機の色や絵文字で盛る装飾も避ける。日本語の推敲は yomiyasu に任せる。

## 数字と出典

- 載せる数字、事例、固有名詞は一次資料で確かめ、出どころを1行ずつ控える(数字、何の数字か、出典、URL、時点)。見つからない数字は作らず「未確認」と書く。
- 同じ指標を複数のページに書くときは、値、単位、丸めの桁、時点をそろえる。
- 用語は1資料1表記。略語は初出で正式名と併記する。表紙とタイトルには略語を使わない。

## 確かめ方

- 同じ作りのページを5枚以上に広げる前に、代表の1枚を発表者に見せる。確認前に広げると、同じ欠陥が全ページに複製される。
- 1件の指摘は、指摘されたページだけでなく、同じ作りの全ページに当てはめる。消すよう頼まれた要素は、書き出した後の全ページから消えたことを確かめてから報告する。
- 機械の検査が全部通ったときほど、測れていない所を疑う。画像の縦横比、はみ出し、題と画像の食い違い(「水もない」と書いた図に水が写っている)は、書き出した画像を目で見ないと分からない。
- 「確かめた」と報告するときは、見たページの番号を書く。全ページと書くのは全ページを見たときだけ。
- 指摘を受けたら、まず最新の版で再現するかを確かめてから直す。

## 文脈を知らない読み手に読ませる(使うときは発表者に確かめる)

原文は、作り方を伏せた別のエージェントにデッキを読ませる工程(フレッシュアイ・レビュー)を最後に置く。co-write-slide では聞き手の集団の代わりにはならないが、発表者にもAIにも見えない食い違いを拾うのに使える。サブエージェントは使用量が多いので、使うかどうかは発表者に聞く。

- 渡すのはデッキのファイルだけ。作り方、スキル、こだわった点は伝えない。
- 見てもらう点: 日本語の引っかかり、タイトルだけを通し読みしたときの話の飛び、タイトルと図の食い違い、根拠のない評価語、既出ページの焼き直し、数の食い違い。
- 返ってきた指摘は全部直さず、1件ずつ採用、不採用、保留を決める。意味が変わる言い換えや構成の組み替えは、発表者に委ねる。
- 1回回したら止めて、続けるかを発表者に聞く。

## 登壇の資料として

- 持ち時間から枚数を決める。目安は1枚40秒前後(7分なら本文8〜10枚)。
- 声で補える資料なので、「大きい見出しと小さい説明文」の2段にしない。説明は大きい文字の中に必要最低限だけ入れる。
- 自分たちの思いを語る文は控えめにし、動機は1回だけ短く言う。

## 取り入れないもの

| 原文の規則 | 取り入れない理由 |
|---|---|
| タイトルは常体、です・ます禁止 | 勉強会の発表は話し言葉で、文体は発表者が決める |
| 本文11枚以上なら全体マップと章扉を必ず置く | 構成は発表者のもので、型から決めない |
| 最後のページはロゴと連絡先だけ | 締めは発表者が決める(co-write-slide のフェーズ2) |
| HTML のパーツ集、PPTX への変換、機械検査のスクリプト | Marp で作る co-write-slide には合わない。必要なら原文のリポジトリを直接使う |
| AI の活用を扱う資料で Jinba に触れてよい、裏表紙に制作クレジット | 提供元の製品の話で、発表者の資料には関係ない |
