# 発表スライドを一緒に作る

発表の材料は二か所にある。

- 発表者の頭の中: なぜそれに夢中になったか、何に感心したか、何を意図して外したか。どこにも記録が無いことが多い。
- ワークスペースとWeb: 過去のスライド、メモ、リポジトリ、Issue、スクリーンショット、公式の報道。発表者自身が忘れているものもある。

フェーズ0で両方を集め、フェーズ1でそれを全部スライドにする。削るのはその後で、発表者の仕事。

## フェーズ0: 材料を探し、発表者から聞き出す

### 材料の探し方

一次資料を先に探す。要約より、その時点で本人が書いた言葉のほうが強い。

1. GitHubの活動。`gh search prs/issues/commits --author <本人> -- -org:<会社のorg>`。社内向けの発表で会社のorgの活動を話す意味は薄いので外す。コミット検索は1,000件で打ち切られるので、日付で区切って取る。Issueは本文とコメントまで読む。思考の記録はそこに残っていることが多い。
2. 過去の登壇資料と、その準備メモ(構成案、grill-meの記録、素材カード)。
3. 活動記録(amemなど)。これはエージェントが書いた要約で、本人の言葉ではない。手がかりとして使い、引用はしない。
4. バックアップや共有フォルダに置かれた生の記録(会議メモ、面談の記録、スクリーンショット、提出物)。
5. 公式の報道。発表者が置いた二次資料(Web調査のレポートなど)は、公式の一次資料と突き合わせる。抜けや食い違いがあることを前提にする。

材料は、発表者が置いてくれたメモ置き場に、1題材1ファイルのカードとして書く。索引(README)と時系列を最初に作る。

### 聞き出し方

- 質問は一度に一つ。答えによって次の質問が変わるべきだから。
- 選択肢で答えられる形にする(プロジェクトの規約に従う。例: A / B / C / それ以外)。
- 答えを受けたら、まずカードに記録してから次の質問を作る。
- カードでは、本人の言葉と自分の推測を分けて書く。推測は「推測」と明記し、確認したら書き換える。推測が外れたら、外れたことも残す。
- 発表者の頭の中にしか無いこと(動機、確信したきっかけ、意図して外したもの)は、自分の知識で補って断定しない。聞いて記録する。
- 聞く価値があるのは、答えで盛り込む中身が変わる事実だけ。どのチームか、同じプロジェクトか、何が決め手だったか。
- 構成の決めごと(持ち時間、話の流れ、核のメッセージをどこで言うか、スライドの言語)も一つずつ聞く。発表者が流れを示したら、それに従う。

記録が見つかったら、ワークスペースのどこにあったかを答えと一緒に示す(「`_study` にFelt Lightningの名前がありました」)。発表者の記憶を呼び起こすのは、具体的な現物であることが多い。

## フェーズ1: 全部盛りのスライドを書く

### 全部盛りの意味

- 手元の材料をすべて入れる。削る候補、比重、持ち時間の配分を先回りして聞かない。
- 「概要だけでいい」は1項目あたりの深さの指定で、材料を減らす指示ではない。
- 版を上げて構成を組み直すときに、前の版にあった材料を落としていないか確かめる。
- スクリーンショットは、なるべく全部盛り込む。

### 1項目の書き方

技術の名前を並べるだけでは、どの技術が何のためにあるのかが伝わらない。1項目(1チーム、1プロジェクト)ごとに次の順で書く。

1. 社会的意義(何を、誰のために解くか)を1行
2. 成し遂げること(最終的に何が出るか)
3. 役割の表: 役割 | データ | 技術。データ(入力として読むもの)と技術(手法、道具、形式、仕組み)を混ぜない
4. 出典の1行。未確認のものは「未確認」と書く

テクニカルタームは説明を付けずにチップ(インラインコード)で並べてよい。聴衆が各自で調べられる。

### スクリーンショットの扱い

- ブラウザのタブ、URLバー、ブックマーク、OSのタスクバーは切り落とす。参加者の名前やメールアドレスが写り込んでいる。
- 画面の数字を説明に書くときは、画面から読み取った値をそのまま使う。
- 他人の成果物の画面は「社内共有のみ」と明記する。
- 2枚並べるときは幅を指定し(16:9で各540px前後)、1枚のときは高さで指定する。幅で指定すると縦長の画像が下にはみ出す。

### 既存のデッキの再利用

過去の登壇資料をコピーして直さない。元のデッキから毎回読み込んで組み立てるスクリプトを書き、画像のパスを付け替える。元を直せば組み立て直すだけで反映される。

### Marpの罠

- 本文の行の直後に `---` を置くと、区切りではなく見出し(setext)になり、2枚が1枚に結合する。`---` の前後には必ず空行を入れる。
- 既定のテーマは縦中央に寄せる。表紙以外は `section:not(.title) { place-content: start stretch; }` で上詰めにする。
- `<!-- _style: ... -->` は効かないことがある。収まらないときは表の行をまとめる。
- PDFやPNGの書き出しにはPlaywrightのChromiumを使う。snapのChromiumは `/Workspaces` を読めず、画像の抜けた成果物ができる。Ubuntuでは `CHROME_NO_SANDBOX=true` が要る。
- marp-cliは標準入力を閉じて実行する(`</dev/null`)。開いたままだと入力待ちで止まる。

### 書いたら必ず見る

- 全スライドをPNGに書き出し、一覧画像にして目で見る。はみ出し、結合、画像の崩れは、ソースを読んでも分からない。
- 版ごとに `slides.vX.md` として控えを残す。
- 日本語の推敲(yomiyasuなどのスキル)をかける。太字とダッシュ記号は使わない。和文と英数字の間の空白、行末のコロン、比喩動詞(名指す、落とす、活きる)を直す。チップとHTMLとコードには触れない。
