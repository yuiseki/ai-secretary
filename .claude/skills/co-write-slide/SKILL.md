# 発表スライドを一緒に作る

このスキルは、谷口忠大の記号創発システムと集合的予測符号化の考え方に立っている。兄弟のco-write-issueとco-write-prと同じ考え方に基づいていて、違うのは参加者の数と、最後に判定する集団がいること。

人は他者の頭の中を覗けない。正解を持っている教師もいない。それでも、観測の違う者どうしが提案と受容・棄却を繰り返すと、共有されたサインと、その意味の理解が両方に育つ。メトロポリス・ヘイスティングス名付けゲームでは、これが中央に観測を集めない分散ベイズ推論になる。比べられた条件のうち、交信しない場合と、相手の提案を全部受け入れる場合はどちらも劣る。

発表スライドに当てはめると、エージェントは三者いる。

- 発表者。なぜそれに夢中になったか、何に感心したか、何を意図して外したか、どう捉えているかを知っている。どこにも記録が無いことが多い。
- AI。ワークスペースとWebを観測できる。過去の資料、リポジトリ、Issue、スクリーンショット、公式の報道。発表者自身が忘れているものもある。
- 聞き手の集団。発表を聞いて、自分の知識と関心に照らして受け取るか、素通りするか、問い返す。

スライドは共有するサインで、目標は発表者がどのスライドについての質問にも自分の言葉で答えられること。デッキが良く見えることは目標ではない。

## フェーズ0: 発表者とAIの名付けゲーム

### AIが観測する

一次資料を先に探す。その時点で本人が書いた言葉は、後から書かれた要約より強い。

GitHubのIssueとPRとコミット、過去の登壇資料とその準備メモ、会議や面談の記録、スクリーンショット、提出物、公式の報道を当たる。エージェントの作業記録は手がかりとして使い、引用はしない。本人の言葉ではないから。発表者が置いてくれた二次資料(Web調査のレポートなど)は、公式の一次資料と突き合わせる。

見つけたものは、発表者の用意したメモ置き場に、1題材1ファイルのカードとして書く。

### 提案して、受容か棄却を受ける

AIの提案は二種類ある。見つけた現物と、そこから立てた仮説。どちらも発表者に判定してもらう。

- 提案は一度に一つにする。判定によって次の提案が変わるべきだから。
- 選択肢で答えられる形にする。発表者が「それ以外」を選んだときは、その答えに一番大きな情報がある。
- 判定を受けたら、まずカードに記録してから次の提案を作る。棄却された仮説も、棄却されたことと一緒に残す。
- カードでは、発表者の言葉とAIの推測を分けて書く。推測は「推測」と明記する。

役割は交代する。発表者が答えを出したら、今度はAIがそれを現物で確かめる側に回る。発表者が「どこかのチームが当然のようにDuckDBを使っていて感心した」と言ったら、リポジトリを探して、どのチームのどのコードかを示す。

- Prefer: 「`_study` のREADMEに『This repository is not trying to build Felt Lightning.』とありました。Felt Lightningの核心はどれでしたか」
- Avoid: 「Felt Lightningは、編集差分をタイルに合成する仕組みです」(発表者の頭の中にしか無いことを、AIの知識で補って断定している)

全部受け入れると、AIの仮説が発表者の捉え方を上書きする。全部棄却すると、AIの観測が入らない。どちらも劣る。

### 止まる条件

材料が無ければ提案しない。出典の無い主張を事実として書かない。発表者の頭の中にしか無いことを、AIの知識で埋めない。

## フェーズ1: 全部盛りのデッキを提案として書く

フェーズ2で聞き手が受容・棄却を判定できるように、判定の候補を全部並べる。

- 手元の材料を全部入れる。削る候補、比重、持ち時間の配分を、この段階で発表者に聞かない。それは聞き手の判定を、発表者とAIの推測で先取りすることになる。
- 「概要だけでいい」は1項目あたりの深さの指定で、材料の量の指定ではない。
- 版を上げて構成を組み直すときに、前の版にあった材料を落としていないか確かめる。
- スクリーンショットは、なるべく全部入れる。

1項目(1チーム、1プロジェクト)ごとに、何を誰のために解くか、最終的に何が出るか、どの技術が何の役割を果たすかを書く。技術の名前を並べるだけでは、聞き手は判定できない。

- Prefer: 役割 | データ | 技術 の表。「電柱や街灯を画像から見つける | | YOLO-CSE」
- Avoid: `3D modelling` `5G network planning` `site selection` とだけ並べる

データ(入力として読むもの)と技術(手法、道具、形式)は混ぜない。各スライドに出典を1行添え、確かめていないものは「未確認」と書く。

話の捉え方は発表者のものにする。発表者が流れや核のメッセージを示したら、それに従う。AIがもっと良いと思う構成があっても、提案として一つ出し、判定を受ける。

書いたら全スライドを画像に書き出して見る。崩れはソースを読んでも分からない。版ごとに控えを残す。作り方の具体的な注意は [references/deck-building.md](references/deck-building.md) にある。

## フェーズ2: 聞き手の反応で削る

この段階は、まだ実際に回していない。書いてあるのは方針だけ。

聞き手は毎回発表者に尋ねる。同じスキルを、小さな勉強会にも、社内の勉強会にも、国際会議にも使う。聞き手が誰かで、何が受け取られ何が素通りされるかが変わる。

- 聞き手は誰か。人数、言語、どこまで前提を共有しているか。
- 本番の前に、少人数のリハーサルや別のエージェントに見せるか。
- 反応をどう集めるか。出た質問、詰まった箇所、素通りされた箇所。

削るのは、反応を受けた発表者。AIは反応を記録し、どのスライドへの反応かを対応づけ、削る候補を提案として出して判定を受ける。反応の無いスライドをAIの判断だけで削らない。

## 公開する前に

- 書いた数字はすべて、どこから取ったか言える。
- 観測したことと推論したことが混ざっていない。
- 他人の成果物の画面は、出してよい範囲(社内だけか、公開か)を発表者が決めている。
- 発表者が、どのスライドについての質問にもAIに戻らず答えられる。

最後の項目が本当の検査になる。答えられなければ、フェーズ0に戻って聞く。発表するのは発表者で、スライドは発表者の名前で出ていく。
